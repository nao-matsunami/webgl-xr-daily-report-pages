制作に使えそうな技術メモProduction notes

SPZ v4 対応では、loader の format branch、zstd、layout 差分、versioned test asset を必ず分けて考える。視点依存の艶を持つ splat ほど、decode が遅れると違和感が強いので、最初に出す低密度 splat でも specular / sheen の方向性は維持したい。CSM は 4 cascade を 1 atlas に入れるため、cascade split、texel snapping、boundary blend を debug overlay にすると、影の揺れがバグか演出か判断しやすい。FSR 1 は EASU と RCAS を分けると、低解像度化で失った構造をどこで拾い、どこで sharpen しているか説明しやすい。textureFloatBlendable は WebGL2 では EXT_float_blend、WebGPU では float32-blendable feature に依存するので、粒子・bloom・accumulation を使う作品では fallback color を設計しておく価値がある。NodeMaterial compile / WebGLNodesHandler の文脈では、事前 compile が scene / camera / lights / fog / environment のどこまで見るべきかを明示することが、ロード中の黒画面や初回 frame hitch を減らす。

For SPZ v4 support, keep loader format branches, zstd, layout differences, and versioned test assets separate. Splats with view-dependent sheen become visually wrong if decoding lags, so even the first low-density pass should preserve the direction of specular / sheen response. For CSM, packing four cascades into one atlas makes cascade split, texel snapping, and boundary blending useful debug overlays. For FSR 1, separating EASU and RCAS makes it easier to explain where low-resolution structure is recovered and where sharpening happens. textureFloatBlendable depends on EXT_float_blend in WebGL2 and float32-blendable in WebGPU, so particle, bloom, and accumulation-heavy work should design fallback colors. In the NodeMaterial compile / WebGLNodesHandler context, being explicit about scene, camera, lights, fog, and environment dependencies helps reduce black first frames and initial hitching.
