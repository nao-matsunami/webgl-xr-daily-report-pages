注目事例と何が面白いかNotable examples and why they matter

最も使い勝手が良いのは PlayCanvas #9274。深度は通常 shader 内だけの素材になりがちだが、`SceneDepthReader` は「小さな矩形を読み戻し、1-2フレーム遅れて判断へ戻す」という設計なので、UIではなく作品のふるまいとして深度を使える。例えば pointer 近傍の8x8サンプルだけを読み、近い面があれば焦点を合わせ、何もなければ `Infinity` として空間を抜ける。three.js #34431 はテストの話だが、workgroup / subgroup / barrier の期待値を可視化すれば、compute shader の内部状態がそのままライブ演出の拍になる。Babylon.js #18861 は OpenPBR の backend一致が主題で、見た目の差を潰す更新だが、制作面では「差が出る箇所」を明示的に比較画面へ出せる。PR #18865 の Adreno 問題は特に重要で、`r32float` filterability や `highp int` の有無が画の有無に直結するため、モバイル向けには品質低下ではなく別のシェーダールートを用意する考え方が必要になる。

The most actionable item is PlayCanvas #9274. Depth often remains shader-only material, but `SceneDepthReader` turns a small sampled rectangle into a delayed CPU-side decision, letting depth affect behavior instead of only shading. A pointer-centered 8x8 sample can focus when a close surface exists and pass through space when the read returns `Infinity`. three.js #34431 is nominally about tests, but visualizing expected values for workgroups, subgroups, and barriers turns compute internals into a rhythmic live surface. Babylon.js #18861 removes backend differences, yet for production it also reveals where such differences should be displayed in comparison views. PR #18865 is especially relevant for mobile: `r32float` filterability and `highp int` support can decide whether IBL shadows appear, so mobile paths need deliberate alternate shader routes rather than vague degradation.

制作に使えそうな技術メモProduction notes

`SceneDepthReader` 的な設計では、毎フレーム全画面を読むのではなく、pointer、gaze、reticle、音のピーク位置などに限定した小矩形を読むのが現実的。結果が1-2フレーム遅れる前提で、視覚側は即時反応、論理側は遅延確定という二層に分けると破綻しにくい。reciprocal depth は半透明splatの輪郭でfar clipに引っ張られる問題を緩和する考え方として有用で、可視化では `alpha / depth` と `1 / farClip` の混合として扱うと理解しやすい。TSL atomic workgroup array は WebGPU 前提なので、WebGLでは atomic を実行するのではなく、bin、contention、barrier、subgroup vote の形を先にデザインする。bitcast / storage texture の型不一致は、色がおかしいではなく「コンパイルできない」「store値がcoerceされる」種類の事故なので、サンプルにはshader compile errorを画面下部へ出す保険を残す。Babylon.js #18865 のようなモバイルGPU差は、`highp int`、float texture filterability、half-float fallback をチェックリスト化しておく。

For a `SceneDepthReader`-style system, read a small region around pointer, gaze, reticle, or audio peak positions rather than the full frame. Since results arrive one or two frames later, split the design into immediate visual response and delayed logical confirmation. Reciprocal depth is useful for semi-transparent splat silhouettes that would otherwise pull toward the far clip; visualizing it as a blend of `alpha / depth` and `1 / farClip` makes the tradeoff legible. TSL atomic workgroup arrays are WebGPU-only in practice, so WebGL prototypes should design binning, contention, barriers, and subgroup votes before executing real atomics. Bitcast and storage-texture type bugs are compile/store failures rather than simple color mismatches, so keep shader compile errors visible in the sample. Babylon.js #18865 suggests a mobile checklist: `highp int`, float texture filterability, and half-float fallback.

サンプルデータの可能性と組み合わせ考察Possibilities for the sample data and combinations

今日の2本は、入力値そのものを保存して育てやすい。Scene Depth Reader Probe は pointer位置、read rect、focus depth、Infinity率、queue age、cap到達フラグをログ化できる。これを音反応と組み合わせるなら、低域でread rectを広げ、中域でfocus capを動かし、高域でreadback pulseを発行する。WebXRと組み合わせるなら、gaze reticle近傍のdepthを読み、近い面だけにwhite balance lensやretroreflectionを出す。TSL Atomic Subgroup Scope は bin pressure、subgroup threshold、bitcast mismatch、viewport quadrantをログ化できる。これを展示演出に使うなら、観客密度や端末性能差をatomic contentionとして見せ、混雑が高いほどfluid粒子が大きくなり、mobile fallback時は半透明で軽い表現へ移る。中長期では、これらのログを日次サンプル横断で蓄積し、どの入力が良い画へ繋がったかを後から再生できる形にする価値がある。

Both samples are easy to grow as logged input systems. Scene Depth Reader Probe can log pointer position, read rectangle, focus depth, Infinity ratio, queue age, and focus-cap hits. Combined with audio, bass can widen the read rectangle, mids can move the focus cap, and highs can issue readback pulses. Combined with WebXR, gaze-reticle depth could trigger white-balance lenses or retroreflection only on nearby surfaces. TSL Atomic Subgroup Scope can log bin pressure, subgroup threshold, bitcast mismatch, and viewport quadrant. In an installation, audience density or device-performance differences can appear as atomic contention; higher contention increases fluid particle size, while mobile fallback switches to lighter translucent rendering. Medium-term, these logs should be accumulated across daily samples so successful input-to-image mappings can be replayed and compared later.
