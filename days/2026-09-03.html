Velocity buffer、datamosh、fluid粒径を遅延するGPU状態の表現にする

Turning velocity buffers, datamosh, and fluid particle size into delayed GPU-state expression

three.js の MeshVelocityMaterial / TSL subgroup indexing / native linear indexing、PlayCanvas の ImmediateBatch typed array retention / volumetric fog resize fix / SceneDepthReader継続、Babylon.js の IBL shadow for ShadowOnlyMaterial / fluid per-particle size / white balance / MultiTexture を調査した。前回の depth readback と atomic diagnostics を受け、今日は「速度バッファやreadbackの遅延をdatamosh的な履歴表現にする」方向と、「粒子サイズ・IBL shadow・モバイルfallbackを品質モードとして見せる」方向へ進め、本命サンプルと派生サンプルを2本実装した。

Today covers three.js MeshVelocityMaterial, TSL subgroup indexing and native linear indexing, PlayCanvas ImmediateBatch typed-array retention, volumetric fog resize handling and the continuing SceneDepthReader thread, plus Babylon.js IBL shadows for ShadowOnlyMaterial, fluid per-particle size, white balance, and MultiTexture. Building on depth readback and atomic diagnostics, the direction shifts toward using velocity-buffer/readback delay as datamosh-like history and showing particle size, IBL shadowing, and mobile fallback as visible quality modes. Two runnable WebGL samples were implemented.

制作に使えそうな技術メモProduction notes

velocity buffer を使う場合、描画物の前フレーム位置と現フレーム位置を分けて管理し、screen-space velocity を postprocess に渡す。WebGLの最小試作では実バッファを持たず、ポインタの前回値と現在値の差を velocity と見なすだけでも表現検証になる。datamosh は色の崩れではなく、motion vector で参照UVをずらす処理として設計すると制御しやすい。PlayCanvas #9286 の教訓は、lineやdebug overlayも演出に使うなら JS 配列 push の膨張を避け、Float32Array の容量維持に寄せること。PlayCanvas #9283/#9275 からは、resize / destroy / async read の未完了状態を捨てずに、画面上で小さな dropout pulse として扱う設計が見える。Babylon.js #18863 の per-particle size は、音量、速度、深度、subgroup/bin pressure と相性が良い。

For velocity buffers, keep previous and current object positions separately and pass screen-space velocity into postprocessing. In a minimal WebGL prototype, pointer delta can stand in for real velocity. Datamosh is easier to control when designed as motion-vector UV offset rather than arbitrary color corruption. PlayCanvas #9286 suggests using retained Float32Array capacity for line/debug overlays that become part of the show. PlayCanvas #9283/#9275 suggest surfacing resize, destroy, and pending async-read states as small dropout pulses instead of hiding them. Babylon.js #18863's per-particle size pairs well with audio, velocity, depth, and subgroup/bin pressure.

サンプルデータの可能性と組み合わせ考察Possibilities for the sample data and combinations

今日の2本は、入力値と描画状態をデータとして扱うと発展しやすい。1本目は pointer velocity、readback pulse、mode、fog dropout timing をログにすれば、ユーザーの動きがどこでdatamoshを起こしたかを後から再生できる。2本目は particle size、shadow strength、layer id、fallback flag を持てるので、MediaPipeの手速度、Web Audioの低域、WebXRの床検出、商品画像の透明shadow catcherと組み合わせやすい。展示では、来場者の速い手振りだけが液体粒子を太らせ、床影は半拍遅れて追う。Web演出では、ページ遷移時のvelocity bufferを次ページの液体shadowへ渡すと、単なるtransitionではなく「前ページの運動量が残る」表現になる。

Both samples become more useful when their inputs and render states are treated as data. The first can log pointer velocity, readback pulse, mode, and fog-dropout timing, allowing replay of where user motion caused datamosh. The second can expose particle size, shadow strength, layer id, and fallback flags, making it easy to combine with MediaPipe hand speed, Web Audio bass, WebXR floor detection, or product-image transparent shadow catchers. In an installation, only fast hand gestures thicken liquid particles while floor shadows follow half a beat later. On the web, passing page-transition velocity into the next page's liquid shadow creates a sense that motion from the previous page remains.
