表現・インタラクションのアイデアExpression and interaction ideas

短期案は「XR Eye Resolve Fog Scope」。実 XR を立ち上げず、1枚の fragment shader で左右眼の微小差分、resolve error、fog coverage、padding residue を疑似的に描く。ポインタは stereo resolve lens になり、ドラッグ方向で左右眼の差分軸が傾き、クリック/Space で fallback pressure が上がる。昨日の MRT fog refraction とは、color/id/fog/padding の4レーンから、stereo/resolve/fog/padding の4レーンへ変えた関係。中長期案は、この lens を three.js WebXR の左右眼 capture、Babylon WebGPU-XR fallback state、PlayCanvas GSplat chunk/fog debug に接続すること。

The short-term idea is XR Eye Resolve Fog Scope. Without launching real XR, one fragment shader simulates left/right-eye micro-differences, resolve error, fog coverage, and padding residue. The pointer becomes a stereo resolve lens; dragging tilts the eye-disparity axis; click or Space raises fallback pressure. It extends yesterday's MRT fog refraction by shifting from color/id/fog/padding lanes to stereo/resolve/fog/padding lanes. Longer term, connect this lens to three.js WebXR eye captures, Babylon WebGPU-XR fallback state, and PlayCanvas GSplat chunk/fog debugging.

制作に使えそうな技術メモProduction notes

XR の postprocess は、片目ごとの色・深度・fog を合成した後に何を共有し、何を個別に残すかが重要。single-pass/multiview は CPU/GPU コストを下げる一方、左右差分の検証を見落としやすいので、resolve error を色に出す debug pass を持つとよい。fallback 設計では、WebGPU-XR が使えない場合に単に 2D に落とすのではなく、機能不足を fog density、grain、色収差、入力遅延の演出へ変換できる。KHR_interactivity を視野に入れるなら、ポインタ選択、イベント名、数値パラメータを shader uniform に直接渡せる小さな bridge を作る。PlayCanvas の JSDoc/型整備は、サンプル生成や社内テンプレートで `renderTarget`, `texture`, `fog`, `splat` の API 誤読を減らす材料として見る。

For XR post-processing, decide which color, depth, and fog data is shared after eye composition and which data stays per-eye. Single-pass and multiview reduce CPU/GPU cost, but can hide eye-specific defects, so a debug pass that colors resolve error is useful. For fallback design, do not simply drop to 2D when WebGPU-XR is unavailable; convert missing capabilities into fog density, grain, chromatic offset, or input-latency staging. If tracking KHR_interactivity, build a small bridge that passes pointer selections, event names, and numeric parameters into shader uniforms. PlayCanvas JSDoc/type hardening is useful as material for sample generation and internal templates, reducing API misreads around render targets, textures, fog, and splats.

サンプルデータの可能性と組み合わせ考察Possibilities for the sample data and combinations

今日のサンプルは、pointer、drag velocity、pressure、mode を入力にし、stereo disparity、resolve error、fog coverage、padding residue を描画状態として持つ。この4値を実データに置き換えると、XR 作品では左右眼の快適性を演出として可視化し、建築・商品 splat では見えない品質指標を鑑賞可能な霧や光に変換できる。Web Audio と組み合わせるなら、低域を fog、中域を eye disparity、高域を padding flicker に入れると、音楽に合わせて空間の安定性が揺れる。MediaPipe と組み合わせるなら、手の開閉を fallback pressure、顔の向きを eye axis に割り当てると、身体入力で視差の破綻を“照らす”体験になる。WebXR では headset がない環境にも同じ shader overlay を出し、fallback 画面を退屈な警告ではなく、体験の入口として使える。

Today's sample uses pointer, drag velocity, pressure, and mode as inputs, with stereo disparity, resolve error, fog coverage, and padding residue as render states. Replacing those four values with real data could visualize eye comfort in XR works or turn hidden quality metrics in architectural and product splats into viewable fog and light. With Web Audio, bass can drive fog, mids eye disparity, and highs padding flicker, making spatial stability move with music. With MediaPipe, hand openness can become fallback pressure and face direction can become the eye axis, letting the body illuminate disparity failures. In WebXR, the same shader overlay can appear on non-headset fallback screens, turning an otherwise dull warning into an entry experience.
